# 把材料、AI 评价和人工判断放在同一个工作台

评一批作品，耗时的不只是打分。前面要收齐材料、找到对应作品，过程中要按标准写出评价，最后还要核对人工修改和最终成绩。材料一多，评委很容易把时间花在来回查找和重复整理上。

我做这个系统，希望把这些步骤连接起来：材料集中查看，AI 先给出维度分和评语，评委据此复核，再明确采用哪个结果、什么时候可以确认输出。

## 实际评审中的使用反馈

系统历次迭代累计用于约 **2000份作品真实评审**。评委会直接复用 AI 评语，把分数作为重要参考，也给出了积极反馈。

按实际使用经验估算，内部评审整体用时比人工流程节省 **80%以上**，包含材料收集整理、评分与复核，前期重复收集作品文件的改善尤其明显。这个数字没有做严格配对计时，也不代表模型评分准确率。

## 先看材料，再看评分

我把材料和评分版本放在同一套应用中，方便评委对照源代码、交互记录、截图或视频状态理解评分依据。评分页展示维度分和评语，让评委能看出具体判断，而不仅是一个总分。

## AI 给出过结果，还需要有人确认

我在流程里把三件事分开：AI 生成过哪些结果、人工选择采用哪次结果、哪个版本已经最终确认。否则，一次重试或后续修改就可能让人弄不清哪个分数才算数。

系统分别记录评分尝试、采用决定和最终锁定；异常进入复核流程，强制复核的结果不能自动采用。详细的材料校验、标准版本、重试和结果选择规则放在[流程说明](workflow.md)中。

## 失败也要有下一步

模型请求失败、证据不足和人工不同意评分，需要不同的处理方式。系统保留状态和尝试记录，通过复核工单登记处理决定。

![界面为失败案例登记同模型重试决定](screenshots/retry.png)

图中是另一个失败案例，我实际登记了“同模型重试”决定，没有继续执行模型请求。另一个旧演示案例因为状态不符合采用要求被拒绝，原因和操作记录也保留在[证据页](evidence.md)。

## 我负责的部分

我负责材料要求、评价规则、复核和交付流程，借助 AI 编程工具实现前后端，再对照实际业务进行验收。技术使用 React、TypeScript、FastAPI、SQLAlchemy、SQLite 和 LLM API。

这里最希望复用的是处理材料、版本、异常和人工决定的方法。换到别的评审业务时，评价标准、证据要求和模型效果仍然需要重新验证。当前应用以单用户本机运行使用，完整代码已在 [ai-scoring-system](https://github.com/chenbaitao88-ctrl/ai-scoring-system) 开源，业务数据不公开。
